# 客製化旅遊規劃 App｜功能修改規劃書

版本：提案 v1.6

日期：2026-10-23

適用平台：iOS、Android，共用 ASP.NET Core API 及 PostgreSQL

狀態：產品需求與開發目標；本機示例原型的已實作範圍與限制見 [時間軸說明](SCHEDULE-EDITOR.md)。未接入的真實資料服務不視為已完成。

## 1. 產品定位與本次目標

這是一個以「使用者今天的能力與喜好」為核心的客製化旅遊規劃 App。使用者先完成簡短問答，App 建立旅行偏好與雷達圖，再依偏好、行程鬆緊度、預算、步數、交通、營業時間和天氣，自動產生單日或多天的第一版完整建議行程，包含每天的住宿、用餐、廁所及有需要時的行李寄放與領取。使用者不必先逐一勾選景點；看到第一版後，可以直接採用，也可以自行勾選、取消、增加、指定必去地點，或在時間軸拖拉活動調整順序與時段，並立即看見整趟行程預估花費、步數與時間的變化。

核心價值是讓使用者知道：**為什麼推薦這裡、選了之後是否負擔得起，以及今天能不能順利走完。**

本次優先完成五個成果：

1. 把問答結果整理為可修改的旅行偏好與雷達圖。
2. 先自動產生符合雷達圖的第一版行程，再提供排序後的附近景點供使用者選擇調整。
3. 第一版及每次調整後，試算包含返程的完整步數、花費與時間；超過精力或預算上限時主動跳出提示。
4. 天氣影響行程時提出具體替代草案，由使用者決定是否採用。
5. 支援多天安排，將住宿、用餐、廁所及行李寄放／領取一併納入首版行程與每次重算。

## 3. 使用者主要流程

```text
首次開啟
  → 簡短問答
  → 偏好摘要與雷達圖：確認／修改
  → 設定旅遊日期／天數、每日住宿、抵離時間、預算範圍與行李需求
  → 系統依雷達圖分配多日景點，串接住宿、用餐、廁所及行李任務，產生第一版完整建議行程
  → 顯示選點理由、順序、到離時間、交通、休息及總負擔
  → 若完整步數或花費超限，跳出提示並提供調整方式
  → 使用者可直接採用，或自行勾選／取消／新增／標記必去
  → 在每日時間軸拖拉景點、用餐等活動，調整順序、時段或日期
  → 修改後重算全程與排序，再次檢查上限、營業時間及天氣
  → 確認儲存
  → 出發前／旅途中檢查變動，必要時提出調整草案
```

回訪使用者沿用已同意保存的偏好，只需確認「今天有什麼不同」。例如平常每天可走 10,000 步，今天可以改為 6,000 步，不必重新填完整份問卷。

## 4. 首次問答與雷達圖

### 4.1 問答內容

建議基本問答控制在約 6–8 題，採單題式畫面；進階條件可以稍後補充。

| 主題 | 問法示例 | 對規劃的用途 |
|---|---|---|
| 預算 | 今天每人想花多少？包含門票、餐飲及當地交通嗎？ | 建立每日金額上限與涵蓋項目 |
| 步行能力 | 今天大約能接受多少步？ | 步數上限；可用輕鬆／一般／健走選項輔助設定 |
| 行程節奏 | 喜歡悠閒停留，還是多去幾個地方？ | 景點停留時間、緩衝與站點數 |
| 交通＋等待額度 | 今天最多願意花多少時間在交通和景點排隊？ | 建立每日交通＋景點等待時間上限，供選景點時扣除 |
| 單次等待容忍 | 單次最多能接受排隊或等車多久？ | 作為額外限制；與每日總時間額度分開檢查 |
| 交通接受度 | 能接受哪些交通工具？單段交通最久多久？最多轉乘幾次？ | 限制交通方式、轉乘及單段移動時間 |
| 休息需求 | 通常走多久會想坐下休息？ | 插入休息窗口與鄰近休息點 |
| 洗手間需求 | 希望每隔多久安排可使用洗手間的機會？ | 檢查路線可達性與時間間隔；可略過或不指定 |
| 興趣 | 喜歡自然、美食、藝術、歷史、購物或親子活動？ | 景點內容匹配與排序 |

地點、日期與天數、同行人數、抵離時間、各晚住宿、入住退房時間、行李需求、餐飲需求，以及每日起終點與時間屬於「本次旅遊設定」，與長期問答分開。無障礙、樓梯、坡度及飲食偏好可列為進階條件；資料不足時顯示未知。

### 4.2 雷達圖呈現

雷達圖用於理解偏好，不是健康評分或旅行能力排名。雷達圖至少包含：消費彈性、步行接受度、交通與等待接受度、行程緊湊度、戶外偏好。「交通與等待接受度」對應交通＋景點排隊的總時間額度；單次候車、單次排隊及單段交通容忍另作細項限制，不在總分中重複加權。

- 所有軸統一為「越外側＝接受程度越高」，並附上實際數字與文字說明。
- 興趣類別使用標籤；洗手間及定時休息使用明確時間設定，不勉強塞入雷達圖。
- 記錄原始答案，再產生 0–100 的顯示值；不能只保存雷達圖分數。
- 未回答的軸標示未設定，不能當作 0 分。
- 預算以本次城市、幣別與金額為準，雷達圖不作為實際金額限制。

摘要示例：「今天預算 A$100、最多 8,000 步、交通＋景點排隊每天最多 180 分鐘、單次候車 15 分鐘、行程偏悠閒、偏好藝術與美食，希望每 90 分鐘有休息機會。」

### 4.3 行程鬆緊度如何影響第一版

「行程緊湊度」是雷達圖的正式軸線，從悠閒、適中到緊湊。它必須直接參與自動選點與排程，而非只影響文字或顯示效果。

| 節奏 | 第一版建議行為 |
|---|---|
| 悠閒 | 較少景點、較充裕停留與站間緩衝、保留自由活動及休息時間，減少頻繁轉場 |
| 適中 | 在景點數、停留、轉場及緩衝之間取得平衡 |
| 緊湊 | 在可行條件下增加景點與時間利用率，適度縮短可調整的自由緩衝 |

緊湊偏好不能覆蓋預算、精力、營業時間、必要休息或預約條件；悠閒也不代表一定少走路。前者是節奏，後者是負擔限制，必須分別檢查。系統不得為增加景點而縮短至不合理的遊覽時間。

第一版應解釋節奏如何影響安排，例如：「依你的悠閒偏好安排 3 站，保留午餐與自由時間。」景點數由當地條件決定，不預設所有城市都固定為同一數量。

## 5. 附近景點推薦與勾選

### 5.1 先產生第一版，再開放自行勾選

系統先依完整偏好和本次條件選出合適景點，產生含交通、休息、營業時間檢查及返程的建議草案。第一版不需要使用者先手動挑站，也不會自動儲存成正式行程。

第一版提供「採用這份行程」與「自行調整景點」。進入調整時，系統已安排的景點顯示為勾選並標示「系統建議」，其他候選依適合度排序。使用者可取消、增加景點或標記必去；調整時保留仍勾選的地點，若條件衝突，提出問題而非默默換掉。

### 5.2 推薦清單

先依使用者指定區域或已允許使用的位置搜尋候選地點，再檢查日期、營業時間與基本限制，最後按適合度排序。清單支援調整搜尋範圍、分類、排序及分頁。

每張景點卡至少包含：

- 名稱、分類、距離／預估到達時間、室內或室外。
- 預估門票、建議停留時間、步行需求、洗手間資訊。
- 景點預估排隊時間，以及加入目前行程後的「交通＋等待」淨增減；查不到時標示未知或待估。
- 推薦理由，例如「符合藝術興趣、室內活動、預估免費入場」。
- 勾選、必去、查看詳情三個操作。
- 資料來源、更新時間與未知欄位的提示。

「勾選」代表目前草案內希望保留的地點；「必去」進一步指定不得默默移除。首次自動選點可以建立系統建議勾選狀態；使用者取消後，後續重算不應擅自加回。其他未勾選景點可作為替代推薦，但不自動加入已確認的行程。

### 5.3 排序規則

推薦排序分成兩層：

1. **可行性檢查**：指定日期是否營業、是否在範圍內、是否符合必要條件。已知不可行項目說明原因；未知條件保留提示。
2. **適合度排序**：綜合興趣、預估花費、步行負擔、移動時間、等待及天氣適合程度。

使用者問答決定各項權重。初期採可解釋的規則評分，AI 可協助理解自然語言需求及生成說明；預算、時間與營業條件仍由程式驗證。

適合度分數不表示「喜歡的機率」。資料缺漏也不能自動視為免費、零等待或零負擔；應分開顯示資料完整程度。

## 6. 預算、體力與時間即時試算

### 6.1 畫面設計

第一版建議行程、景點調整清單及確認儲存畫面，均顯示「完整行程負擔摘要」。範圍包含起點、全部停留點、轉場、場內步行及最後返回終點：

| 指標 | 呈現方式 |
|---|---|
| 預算 | 預估總花費／上限、剩餘金額，拆分交通、門票與餐飲 |
| 步數 | 預估總步數／上限、剩餘步數 |
| 時間額度：交通＋景點等待 | 全程交通時間＋景點排隊時間／使用者設定上限，顯示已用、剩餘及超出分鐘 |
| 當日排程 | 另外顯示預估結束時間及可安排時段，仍計入遊覽、吃飯、休息等所有活動 |
| 舒適度 | 等待、連續步行、休息及洗手間間隔提示 |

若沿用「精力條」，第一版明確定義為步數額度的視覺化，不聲稱能量測人的真實精力。總步數仍需直接顯示；休息可以改善行程節奏，但不能讓已走步數歸零或自動增加步數上限。

### 6.2 每次勾選後重新計算

新增景點會改變前後交通路段、返程、候車與用餐安排，因此試算必須重新計算整條暫定行程，而非把每個景點的固定數值直接相加。

- 總步數＝轉場步行＋場內步行估算＋前往用餐、住宿、寄放／取件、休息及廁所的步行。
- 總花費＝門票＋整條交通行程的票價估算＋餐飲＋住宿＋行李寄放費＋使用者指定預留項目；依每人、每房、每件行李等計價單位換算，避免重複計入。
- **時間指標已用額度＝全程交通時間＋景點排隊等待時間。** 交通包含步行、搭車、轉乘移動與候車，涵蓋住宿、用餐、廁所、寄放／取件及返程等全部路段。
- **當日排程總時長＝交通＋景點排隊＋遊覽＋用餐＋休息＋廁所／寄放／入住等辦理時間＋其他等待與緩衝。** 交通＋景點等待是其中一部分，計算排程總長時不能再重複加一次。
- 遊覽、吃飯、休息及設施使用本身不扣「交通＋景點等待額度」，但仍占用當天可用時間；第一版不能因額度有剩餘就忽略收班、關門或入住時間。
- 餐廳候位、等開門、入住或寄放服務等待列為其他等待，占用排程並檢查適用的單次等待限制；目前主時間指標依使用者定義僅合併交通與景點排隊，不混入全部生活等待。
- 若交通服務已提供包含候車的門到門總耗時，交通額度直接採用該總值，不再額外加候車一次；只提供車上時間時，補入步行、轉乘和候車，且每段只計一次。
- 票價須考慮轉乘、日票或上限等已知規則；無足夠資料則顯示估價範圍。
- 餐飲可先設定每餐預留額度，不因多勾一個景點就多扣一餐。
- 金額以整數最小貨幣單位保存；規劃估算與實際記帳分開。

計算期間保留上一版結果並顯示「更新中」。快速連續勾選時合併請求，過期回應不得覆蓋最新選擇；移除景點後，也要重算並釋放原先預留額度。

### 6.3 完整步數／花費／交通等待額度超限必須跳出提示

判斷時點包括：第一版產生後、使用者勾選或取消景點後、交通或排序改變後、天氣微調後，以及確認儲存前。比較的是遊完整趟的總負擔，不能只比較單一景點或忽略返程，也不必等到實際走完整趟才提醒。

- **精力超限**：完整預估步數 > 對應的步數上限，顯示總量、上限及超出步數。
- **預算超限**：完整預估花費 > 對應的預算上限，顯示總額、上限及超出金額。
- **時間額度超限**：完整交通＋景點排隊時間 > 當日設定上限，顯示兩類分項、總量及超出分鐘。
- 多項同時超限時合併成一個提示，分項列出，不連續跳出多個視窗。恰好等於上限顯示已達上限，不列為超過。
- 使用者關閉提示後，摘要保留超限標記；同一版計算結果不重複彈窗，新調整產生不同超限結果時再提醒。
- 估價範圍跨過上限時顯示「可能超出」；關鍵資料缺失時顯示無法完整確認，不顯示保證未超限。

示例文案：

> 走完整趟預估需要 9,200 步，比你的 8,000 步精力上限多 1,200 步。預估花費 A$118，比 A$100 預算多 A$18。

提示提供「查看調整建議」「回到行程修改」「保留草案」。建議可包含減少一站、換免費景點或改搭車，但每個建議都需重算全程；改搭車雖可能減少步數，也可能增加花費。

自動產生第一版時，應優先尋找不超限的可行方案，不能明知超限卻當作一般完成結果。若必要條件使所有方案都超限，顯示不可行或超限草案與原因，不自行放寬條件。

多日行程需同時顯示每日與全旅程摘要：步數以每日上限分別比較，預算明確區分每日額度與全旅程總額，含住宿、餐飲、寄放及跨城市交通等適用項目。每日超限和全旅程超預算各自提示，不能把多天步數總和直接拿來比單日上限，也不能用其他天的低步數抵銷某天超限。詳見第 15 節。

允許使用者繼續編輯超限草案，但在確認前清楚呈現問題。不得自行提高預算、放寬體力上限或刪除必去景點。門檻顏色需搭配文字與圖示，不能只依紅綠色辨識。

## 7. 順路行程規劃

景點的「推薦排名」和「實際到訪順序」是兩件事。排名第一的景點不一定安排在第一站；正式排序需要考慮位置、交通與時間窗口。

規劃步驟：

1. 確認選定地點、必去標記、固定預約、起終點及當天時段。
2. 取得交通時間矩陣及景點停留估算，依行程鬆緊度決定合理停留與緩衝，保留資料來源與適用時間。
3. 先滿足必去地點、固定預約和營業窗口，再降低折返、移動時間及等待；首次由系統選點，後續以使用者修改後的勾選狀態為準。
4. 將每天住宿、用餐、廁所及有需要的寄放／取件作為正式站點共同排序，檢查營業時間、服務時間窗口及跨日銜接；不是景點排完才附註補上。
5. 驗證預算、步數、交通＋景點等待額度、當日可用時段、返程時間及各項必要條件，輸出可檢查的草案。

營業時間需依旅遊當地日期與時區檢查完整到訪區間，包含休館日、午休、最後入場時間及有提供時的特殊營業日。例如景點 17:00 關閉、合理停留需 60 分鐘，就不能排 16:45 抵達並視為可行；可改早到訪、換日或提示衝突。若須等待開門，也需納入等待容忍、總時間與緩衝。未知營業時間明確標示未確認。

第一版可以用插入排序、局部交換等方法改善小型行程，不宣稱保證全域最佳。若顯示多個方案，可提供「少走路」「少花錢」「少轉乘」供比較。

每站顯示到離時間、停留時間、前往下一站的交通方式與預估耗時；支援拖拉調整，使用者指定的新順序應保留，系統只針對衝突提出建議，不擅自改回自動排序。公車有資料才顯示路線號碼；Metro、Train 等依實際資料呈現，未配置服務時明確說明。

找不到可行方案時，回傳是哪幾項條件衝突。例如「兩個必去景點的開放時間重疊，且交通需 45 分鐘」，讓使用者決定延長時間、換日期或取消其中一站。

## 8. 天氣提醒與行程微調

### 8.1 觸發條件

在出發前、開啟當日行程及使用者手動刷新時，檢查景點所在地和預定到訪時段的天氣。初期以前台檢查為主；背景推播另列後續工作。

把景點標記為室內／室外／混合型，依降雨、氣溫、風況等資料判斷是否需要提醒。具體門檻由產品與測試共同校準，保留使用者可調整的戶外接受度。

天氣預報缺失、時間過遠或資料過期時，顯示無法確認，不宣稱天氣良好。

### 8.2 提醒與替代草案

示例文案：

> 下午植物園的戶外行程可能受降雨影響。要看看把植物園移到上午、下午改為室內活動的方案嗎？

提供「查看替代方案」「稍後提醒」「保留原行程」。替代方案按少改動原則，依序考慮：交換上午下午、調整交通或停留時間、推薦附近室內地點。

產生草案時必須重算路線、花費、步數與結束時間，列出變更前後差異。已完成、正在前往、固定預約及必去站點優先保留；需要變動時說明原因並由使用者確認。

系統不會因天氣刷新就直接覆蓋已儲存行程；版本衝突時重新取得最新行程再比較。

## 9. 建議系統架構

```text
原生 iOS / Android
 ├─ 問答與偏好雷達圖
 ├─ 景點清單、勾選及即時額度摘要
 ├─ 可拖拉行程時間軸、活動清單與地圖
 └─ 天氣提醒、草案差異與確認
             │ 共用 API 契約
ASP.NET Core
 ├─ PreferenceProfile：偏好及本次條件
 ├─ CandidateSearch / Ranking：候選與推薦理由
 ├─ SelectionEstimate：選取後整體試算
 ├─ ItineraryPlanner / ConstraintValidator：排序及可行性檢查
 └─ WeatherImpact / ReplanProposal：影響辨認與調整草案
             │ 提供商介面
 ├─ 地點、交通路由、票價、天氣、設施資料
```

底圖、地點資料、交通路線、天氣及設施資料各自透過介面替換，沿用現有來源識別與顯示限制。切換底圖不代表所有第三方資料可以任意搬到另一張地圖；來源、適用時間與顯示規則需保留。

兩個 App 共享欄位、金額單位、時區及錯誤語義；核心計算由後端負責。前端可以顯示立即的粗估，但不能各自維護一套不同的正式扣額算法。

### 9.2 建議 API（待與前端確認，非現有接口）

- `GET /places/candidates`：附近候選、分頁、適合度及推薦理由。
- `POST /selection/estimate`：以偏好、本次限制及選定地點重算草案；回傳請求版本。
- `POST /itinerary/proposals`：產生完整排序與限制檢查結果。
- `POST /trips/{id}/weather-impact`：檢查天氣影響及可調整區段。

建議先完成 B、C 的完整閉環，再加入 D；不把多人協作、自動訂票／訂房、付款、全城市即時排隊或真實健康推估納入首版。時程需在確認人力與資料來源後估算。

## 11. 驗收案例

| 情境 | 預期結果 |
|---|---|
| 完成問答但未手動選任何景點 | 自動取得完整第一版行程，可直接採用或開啟景點勾選調整 |
| 相同條件只改行程鬆緊度 | 第一版在站數、停留與緩衝配置上反映差異，仍遵守預算與精力限制 |
| 全程 9,200 步、上限 8,000 步 | 主動跳提示，含返程，明列超出 1,200 步 |
| 全程 A$118、上限 A$100 | 主動跳提示，明列超出 A$18；與精力超限合併呈現 |
| 預估值恰好等於上限 | 顯示已達上限，不誤報超過 |
| 17:00 關門、需停留一小時、16:45 才能到 | 改排早時段或提示不可行，不能只檢查抵達當下是否開門 |
| 使用者取消系統首版中的一站 | 重算時保留取消意圖，不擅自加回 |
| 第一次開啟並跳過洗手間問題 | 可繼續，顯示未設定；不自行推論 |
| 相同景點，預算與體力偏好不同 | 推薦順序可不同，且可看到原因 |
| 連續快速勾選／取消多個景點 | 最後額度對應最新選擇，不受較舊回應覆蓋 |
| 移除景點但返程變長 | 重算全程，不能直接退回固定點數而顯示錯誤餘額 |

| 必去景點造成超時或超預算 | 保留選擇並顯示衝突，不默默移除或放寬限制 |
| 景點或洗手間資料未知 | 提醒未確認，不當作免費、開放或可使用 |
| 下午戶外景點遇降雨預報 | 提供局部調整草案及花費／步數／時間差異 |
| 拒絕天氣調整 | 原行程保持原版本 |
| iOS 與 Android 使用同一案例 | 推薦理由、額度、排序與錯誤內容一致 |
| 外部路線或天氣服務失敗 | 可保留草案、重試，並區分示例／估算／未取得資料 |

效能驗收以量測為準：快取試算目標約 1 秒內回應；需外部路由的運算顯示進度與取消入口。正式目標須在固定裝置、網路及景點數量下確認，不把公共展示服務的速度視為保證。

## 12. 資料與使用者控制

偏好問答以規劃所需為限，洗手間需求不要求填寫病史；相關資料可選填、修改及刪除。長期保存必須明確同意，這次臨時調整不自動成為永久偏好。

位置資料採使用時取得，也可以讓使用者自行指定搜尋中心。提醒清楚區分「估算規劃」「裝置量測」與「使用者回報」；不把預估步數當作實際已走步數。

上線前需補上帳號與資料隔離、HTTPS、權限控制、偏好刪除流程及服務監測。原型完成不等於已具備正式多人服務能力。

## 13. 第一版展示建議

以同一位使用者完成一段可理解的故事：

1. 設定 A$100 預算、8,000 步、悠閒節奏、偏好藝術與自然、單次候車最多 15 分鐘。
2. 顯示雷達圖後，系統直接產生第一版行程，說明選點、營業時間、停留與緩衝安排。
3. 使用者開啟「自行調整景點」，再勾選另一站並標記必去。
4. 全程重算為 9,200 步、A$118，跳出合併超限提示；展示刪站或改交通後對兩項額度的影響。
5. 對照悠閒與緊湊偏好的第一版差異，確認緊湊方案也不犧牲營業時間或超過必要限制。
6. 使用明確標示的降雨測試情境，產生室內替代草案，確認後才儲存。

展示資料須區分示例與真實查詢。希望達成的體驗是：使用者每做一個選擇，都能理解它對旅遊負擔的影響，並保有最後決定權。

## 14. 本次補充確認（v1.1）

- 預設為「系統先建議完整第一版 → 使用者看完再自行勾選或調整」。
- 精力以完整行程步數估算，包含返程；預算以完整行程花費估算，超限均須主動提示。
- 營業時間限制適用於首版與每次重排，必須能完成合理停留。
- 行程鬆緊度是雷達圖正式維度，直接影響首版的選點、停留、緩衝與安排密度。


## 15. 多天旅遊與每日銜接（v1.2）

### 15.1 多日規劃單位

多天旅遊不是複製多份單日行程。系統先依各晚住宿、抵離時間及景點開放日分配每天區域與景點，再安排每天的完整時間軸。雷達圖的鬆緊度同時影響每日安排及多天之間的負擔分配。

- 每天有獨立日期、當地時區、起終點、可活動時段、步數上限及已安排站點。
- 一般日從當晚／前晚住宿出發並返回住宿；換住宿日則串接舊住宿退房、新住宿入住及行李任務。
- 抵達日包含抵達、交通、行李處理及入住；離開日包含退房、取行李、交通與使用者指定的抵達交通樞紐時間。
- 優先依區域分天，避免每天來回折返。相同景點預設不跨日重複，住宿、餐飲、廁所等生活站點可以重複。
- 營業時間以「那一天」計算，休館日、預約日期與固定活動不因跨日重排而被忽略。
- 多天均有完整步數與返程計算。可提示負擔集中在某日，但不把較輕鬆一天的剩餘步數轉給另一天。
- 可依使用者感受調整隔日步數上限；不宣稱能精確預測疲勞或自動恢復實際精力。
- 使用者鎖定某天、某站或某筆預約後，調整其餘行程優先保留鎖定內容。若必須更動，先指出衝突並提出草案。

跨午夜交通或活動需以完整日期時間儲存，不能只存「23:30」等時分；費用與步數仍需清楚歸屬日期，不能因跨午夜遺失。

### 15.2 預算與住宿的計價方式

規劃前詢問預算是「每天每人」還是「全旅程總額」，並確認住宿、跨城市交通等項目是否包含在內。

全旅程預估總額由每日項目與跨日項目組成，費用各自保留唯一識別及歸屬，避免把總額和每日明細重複相加。住宿依實際房晚、房數及入住人數換算；寄放依件數與時間，餐飲依用餐人數換算。已付款費用可另外顯示「尚需支付」，但若屬於預算涵蓋範圍，仍計入總花費。

每日任一天步數超限即跳提示；啟用每日預算時，每日超支也提示；全旅程預算超支另外提示。多項問題整合為可展開的提示，指出「第幾天」與超出多少。

## 16. 住宿安排

### 16.1 設定與選擇

使用者可以填入已訂住宿、指定每天住宿，或選擇暫未決定。系統記錄地址、入住日期、退房日期、最早入住／最晚入住、退房時間、使用者已知的行李寄放服務及費用資訊。

若尚未決定住宿，可以先使用使用者指定區域或暫定起終點產生有明確假設的草案，同時提出候選住宿供選擇；必須標示「住宿尚未確認」，不能宣稱已訂房、有空房，或已核實房價。選定住宿後重新計算受影響各日交通、步數與費用。

### 16.2 排程規則

- 每晚住宿及必要入住／退房事件需出現在相關日的時間軸。
- 不能在最早入住之前當作房間已可使用，也不能排到最晚入住之後才抵達。
- 想先寄行李但尚不能入住時，建立獨立寄放站點；住宿有無寄放服務、是否需預約或收費，須有資料依據。
- 同一住宿續住時，不必每天重排入住退房；仍以住宿作為每日路線的起終點。
- 更換住宿要計入搬運行李、退房、移動、入住及等待所需時間，不能當作一般無負擔景點轉場。
- 未知服務時間顯示待確認，並列為草案假設；不能把未知時間視為全天可入住。

此版規劃住宿行程與成本，不自動替使用者下訂或付款。

## 17. 行李寄放與領取安排

行李寄放點是正式行程站點。需要寄放時，系統將「寄放」與「領取」建立為相互依賴的一組任務，納入首版建議，而非只顯示附近寄放點。

### 17.1 需要詢問的資料

行李件數／大致尺寸、是否希望避免帶行李走景點、預計何時可寄放、最後需要取回的時間、是否需要過夜寄放，以及已確認可使用的住宿寄放服務。使用者可以略過並稍後補充。

### 17.2 規劃規則

1. 以沿途可達、服務窗口、估價及繞行成本推薦寄放點，優先考慮已確認可使用的住宿服務。
2. 檢查抵達寄放與取件時間是否都在營業窗口內，包含辦理時間與合理緩衝。
3. 取件必須在寄放之後，且在搭乘交通、離開城市或需要使用行李之前；不能只排寄放而漏排取件。
4. 寄放費、來回交通、步數及服務時間一併納入試算；便宜但繞路很遠的點，不一定是最合適方案。
5. 退房後旅遊再取行李，或入住前先寄行李，依當日動線安排；可直接帶往新住宿時，不強制多插一個寄放點。
6. 隔夜寄放僅在服務資料明確支援時採用。跨日未取回的行李狀態需要延續到隔天，並顯示目前預定存放位置。
7. 服務容量、營業時間或接受行李尺寸未確認時，標示待確認；不可宣稱有位或已預約。
8. 使用者刪除寄放或取件其中一項時，提示配對任務會受影響，重新規劃整組任務。

草案另記錄哪些路段需要攜帶行李，顯示搬運負擔，並依使用者偏好避免過長步行；不能未經定義就把行李重量換算成虛構的健康精力值。

## 18. 廁所與用餐作為正式行程站點

### 18.1 廁所安排

- 依使用者設定的間隔、當日出發時間及最近一次已確認使用時間，安排可到達的廁所停靠窗口。
- 每次停靠顯示位置、預估到離時間、停留時間，以及已知的開放與收費條件；步行繞路和使用時間納入總行程。
- 景點、餐廳或住宿內已有已知可使用廁所時，可以附屬在該站，避免產生重複轉場，但仍在時間軸顯示「廁所」子項。
- 檢查是否需消費、門票或其他入場條件，不能把任何店家廁所視為免費公共設施。
- 無資料時標示待確認並提供候選，若預定間隔內找不到可確認設施，顯示安排缺口，不假裝已滿足需求。
- 未回報實際使用時，只顯示原定停靠時間，不把計畫時間當作真實上次使用時間。
- 使用者可跳過、提前或回報已使用；後續廁所窗口與路線重新試算。系統不把這項偏好當作醫療診斷。

### 18.2 用餐安排

- 先詢問哪些餐次需安排、偏好用餐時間窗口、每餐預算、合理停留時間，以及選填飲食限制。
- 有住宿附早餐或使用者已安排餐食時，標示已涵蓋，避免再安排或重複計價。
- 依每天動線在合適區域安排餐飲站點，檢查餐廳營業時段及已知的供餐／最後點餐時間，不能只用店家關門時間代替。
- 用餐站點和候位、往返交通、停留時間一起參與排序；需要排隊但沒有即時資料時，使用標示的假設或緩衝，不宣稱已取得真實候位。
- 尚未選定餐廳時，仍安排明確的「用餐時段／區域與預算」，標示餐廳待選；選定後用實際估價替換原預留額，不能再加一次。
- 餐廳、菜單、飲食適合程度或價格資料未確認時，保留提示；不保證座位、預約或特殊飲食條件。
- 使用者可更換餐廳或延長用餐；系統重新檢查後續景點營業時間、入住與取件窗口，以及步數與預算。

- 廁所可與已知設施的用餐／景點共站，仍包含時間；缺資料時顯示安排缺口。
- 更換第 2 晚住宿時，重新計算第 2 天終點與第 3 天起點的路線及費用。
- 固定預約、已完成活動、使用者取消項目及已確認住宿在重新排程時保留其狀態。

本次補充的產品方向是：**先自動產生包含生活需求的多日旅程，再讓使用者自行勾選和微調；每次更動重新驗證整段旅程的時間、費用、步數與必要任務。**


## 20. 時間指標定義與選點扣額（v1.3）

### 20.1 使用者設定的時間額度

本 App 的主時間指標明確定義為 **「交通時間＋景點排隊等待時間」**。它代表使用者願意花在移動和排隊上的時間，與行程鬆緊度、整天可活動時段分開設定。

```text
已用時間額度＝所有交通路段分鐘＋所有景點排隊分鐘
剩餘時間額度＝每日額度上限－已用時間額度
本次扣除量＝修改後全程已用額度－修改前全程已用額度
```

若剩餘值小於 0，畫面顯示已超出多少分鐘；進度條可顯示已滿，但不能把超出量隱藏。每天各自設定或套用相同上限，多日總覽可累計顯示，不能用其他天的剩餘額度掩蓋某一天超限。

### 20.2 勾選、取消與重排

- 第一版建議行程產生時先計算並占用相應額度；使用者開啟調整畫面時不能再次扣一次。
- 新增景點會改變進出交通與後續出發時間，因此重新估算全程交通及適用時段的排隊，依淨增減更新額度。
- 候選卡可顯示「加入後約多花 40 分鐘：交通 +15、排隊 +25」，並區分景點本身的遊覽時間。
- 取消景點、換交通、換住宿、移到另一日或重新排序都需要重算；不能只退回景點固定的等待值。
- 新增一站後，若順路排序改善其他路段而使全程耗時降低，應顯示減少多少；不強制所有勾選都只能扣額。
- 首版自動推薦優先找能符合時間額度的路線；熱門景點即使交通很近，也可能因排隊過久而降低排序。
- 交通＋排隊額度、單次等待限制、步數、金額與營業窗口都需檢查，不能用某一項尚有剩餘來忽略其他超限。

### 20.3 數字示例

使用者設定每天交通＋景點等待上限為 180 分鐘。第一版交通 80 分鐘、景點排隊 40 分鐘，已用 120 分鐘，剩餘 60 分鐘。

勾選新景點後，全程交通重算為 95 分鐘、景點排隊重算為 65 分鐘，已用 160 分鐘，剩餘 20 分鐘；這次淨扣 40 分鐘。該景點若遊覽 60 分鐘，這 60 分鐘另外占用當日排程，不再從交通＋等待額度扣除。

若再調整後達到 195 分鐘，跳出「交通與景點等待預估超出 15 分鐘」的提示，並提供少轉場、換交通、換低等待景點或刪站的草案，重新比較步數、花費及時間。

### 20.4 熱門景點等待資料

等待時間需區分即時值、歷史時段估算、人工設定與示例資料，保留來源、適用日期／時段及更新時間。熱門程度不能直接換算成聲稱真實的排隊分鐘。

無可信等待資料時顯示未知，或採明確標示且可修改的規劃假設／範圍。存在未知項時，時間摘要只能表示已知小計或估算範圍，不能保證尚有多少可用額度。已預約／快速通關也不自動當作零排隊。

重排造成到訪時段改變時，需要重新取得或估算相應等待時間，必要時再次檢查路線與營業窗口。等待範圍跨過額度上限時提示「可能超出」，並避免快速勾選時舊估算覆蓋最新結果。

### 20.5 新增驗收案例

| 情境 | 預期結果 |
|---|---|
| 交通 80 分鐘、景點等待 40 分鐘、額度 180 分鐘 | 已用 120、剩餘 60 分鐘 |
| 交通回應總值已含候車 10 分鐘 | 不再重複扣 10 分鐘 |
| 勾選後全程交通增加 15、排隊增加 25 分鐘 | 淨扣 40 分鐘，其他指標同步重算 |
| 景點遊覽 60 分鐘、排隊 25 分鐘 | 主時間指標扣排隊 25 分鐘及全程交通增減；遊覽仍排入時間軸 |
| 交通＋排隊額度尚未用完，但趕不上關門 | 仍提示排程不可行 |
| 取消後改排其他站，排隊時段也改變 | 重算全程，不退回固定舊值 |
| 已用額度 195、上限 180 分鐘 | 提示超出 15 分鐘 |
| 景點等待資料缺失 | 顯示未知／假設，不能按 0 分鐘保證未超限 |

本次修訂僅更新規劃定義，尚未實作 App 或接入真實排隊資料。


## 21. 使用者拖拉排程與時間軸編輯（v1.4）

### 21.1 產品決策

系統第一版是可編輯的建議。使用者有權改變景點放置順序、到訪日期、開始時間和停留長度，也可以移動用餐時段。調整後系統保留使用者的意圖，重新驗證交通、排隊、營業窗口、精力、預算及必要任務。

依 v1.5 補充，主要編輯互動改採「影片剪輯式時間軸＋活動片段」：整段拖動改時間與順序、拉動邊界改停留長度。每日直式清單保留作為閱讀與替代操作；地圖與候選活動以按鈕開啟。詳細規則見第 22 節。

### 21.2 手機互動設計

- 上方切換第幾天／日期，顯示每日步數、預算及交通＋景點等待摘要。
- 主區為直式時間軸，卡片顯示活動類型、名稱、到離時間及停留長度。交通與候車／排隊以卡片間的資訊呈現，跟隨前後活動重算，不能單獨拖離所屬路段或景點。
- 景點、吃飯、休息、廁所、寄放／取件與住宿任務使用一致的活動卡，但以文字與圖示區分類型。
- 使用卡片上的拖拉把手移動，避免一般上下捲動誤觸排序。拖曳時顯示插入位置與預計時間。
- 預設拖到「兩張卡之間」改變先後順序，不要求使用者精準對準每一分鐘；後續時間依合理交通與停留連動試算。
- 要指定精確時間時，點擊時間欄開啟開始時間、停留長度或可接受窗口設定。可吸附到 15 分鐘刻度方便操作，但預約與路由計算保留實際分鐘，不能為吸附而誤改預約。
- 候選／未安排活動可從下方清單拖入當日時間軸，也可按「加入」並選插入位置。移出活動則回到未安排清單，並重新計算額度。
- 跨日移動使用卡片的「移到其他日期」操作；首版不要求使用者拖著卡片跨越多個分頁。目的日與原日都重新驗證。
- 保留「上移／下移」「移到指定時間／日期」等替代操作，讓不方便拖拉的使用者與輔助使用者也能完成相同調整。

依 v1.5 補充，首版互動原型即驗證片段拖動與邊界拉伸；點擊時間精修及直式清單作為替代操作。需特別驗證小螢幕的刻度、捲動與觸控把手是否容易使用。

### 21.3 用餐時段與活動的彈性

用餐以「時間窗口＋預估停留」表示，例如午餐希望在 12:00–14:00 之間開始、停留 60 分鐘；示例並非固定要求。使用者可以拖動午餐，或指定固定開始時間。

- 自由用餐窗口可以隨拖拉及交通改變而調整，仍需檢查餐廳供餐時間與使用者的用餐偏好。
- 已訂餐廳或使用者鎖定的餐次優先固定；不可因拖景點而默默延後。
- 尚未決定餐廳時，保留「午餐／晚餐」的區域與預算佔位卡，讓使用者先安排生活節奏；選定餐廳後替換同一筆活動，避免重複扣餐費。
- 拖拉景點跨過午餐時段後，系統重新檢查後續營業時間、入住、取行李及離開時間；不只交換畫面上的卡片。
- 廁所、休息等自動安排項目可提出跟隨調整建議。超過使用者需求間隔時顯示缺口，不因拖動而默默刪除必要安排。

### 21.4 使用者順序與鎖定規則

資料需分開記錄以下狀態，避免不同意圖混為一談：

| 狀態 | 意義 |
|---|---|
| 必去 | 保留這個地點，不表示時間與順序不可改 |
| 使用者指定順序 | 手動拖拉後的新先後關係，後續計算優先保留 |
| 固定時段 | 開始／結束或預約窗口不可自行挪動 |
| 固定日期 | 不移往其他天，但可在該日可用時段中調整 |
| 可自動調整 | 在指定窗口內可連動試算時間，仍需呈現變更 |

手動移動可調整卡片時，試算後續活動到離時間；遇到固定預約或其他限制時提示衝突。系統不能先擅自刪除活動或把順序改回原版。

使用者可按「讓系統重新建議順序」，明確選擇只調整未鎖定項目或重新產生草案；顯示差異後才套用。保留還原上一動作，以及回到原建議版的入口。

### 21.5 拖拉後的試算與衝突處理

拖曳過程只呈現暫定插入與時間預覽，不在每個手指移動事件呼叫外部路由。放開卡片後更新草案版本，合併快速操作並開始正式試算；運算中顯示「更新交通與等待時間」。舊結果不得覆蓋較新的拖拉位置。

每次至少檢查：

1. 新前後路段、交通方式、候車、景點到訪時段與排隊估算，更新交通＋景點等待額度。
2. 每個活動的到離時間、完整遊覽是否落在營業窗口，以及餐廳供餐時段。
3. 當天可活動時間、預約、入住退房、寄放及取件的依賴與服務窗口。
4. 步數、預算、行程鬆緊度、休息與廁所間隔。
5. 跨日移動後原日與目的日的完整路線、住宿銜接、額度和景點重複情況。

可行時更新時間軸與摘要。不可行時保留可編輯的草案並在相關卡片標示問題，例如「此順序預估 17:15 抵達，景點 17:00 關閉」。提供「移到較早時段」「調整其他未鎖定活動」「還原」等具體選項，由使用者選擇。

步數、花費及交通等待額度超限沿用合併提示規則。與營業／預約等時間衝突分項呈現，不能以確認超限為由把已關門的行程標成可行。無法取得新交通資料時保留使用者編輯，標示尚未驗證，不假裝時間精確。

### 21.6 示例互動

第一版為「景點 A → 午餐 → 景點 B → 取行李」。使用者希望晚一點吃飯，把景點 B 拖到午餐前。

系統試算新順序「景點 A → 景點 B → 午餐 → 取行李」，重新計算交通、景點 B 新時段的排隊、餐廳供餐及寄放點取件窗口。若午餐延至 14:30，但餐廳 14:00 停止供餐，則提示並推薦可供餐地點或調整時間；不自行改餐廳或取消取行李。

### 21.7 開發與驗收補充

第一階段交付影片剪輯式時間軸的片段拖動、停留長度拉伸、時間編輯、未安排清單、跨日移動選單、還原與衝突顯示；不包含多軌疊加等無關的影片剪輯功能。詳細互動以第 22 節為準。

後端試算請求增加使用者順序、固定日期／時段、可調整窗口及草案版本。前端依同一契約顯示結果，不能只在本機換卡片卻保留舊交通或額度。

新增驗收：

- 第一版可不經修改直接採用，也可自由調整景點順序。
- 手動排序後重算仍保留使用者新順序；未經同意不重新最佳化改回。
- 拖拉午餐後，交通、排隊、用餐窗口及後續取件時間全部重算。
- 固定餐廳預約與必去地點可分別鎖定，必去不等於固定時段。
- 跨日移動同時更新兩天額度與住宿銜接，不能複製成兩筆。
- 網路失敗或快速拖拉時，編輯不遺失，舊回應不覆蓋新位置。
- 還原操作恢復對應活動狀態，再取得有效試算結果。
- 不使用拖拉的使用者，也可完成相同排序與時間修改。

本次僅更新互動與排程規格，尚未實作 App 的拖拉排程。


## 22. 影片剪輯式時間軸（v1.5，最新互動方向）

### 22.1 核心概念

使用者所指的拉 bar 是影片剪輯式操作，而不只是清單排序。以一天為一條時間軸，每個景點、吃飯、休息、廁所或行李任務都是一段有開始、結束和長度的活動片段。片段在時間軸的位置代表時間，長度代表停留時長。

依最新確認，第一版編輯原型以直向、由上到下的單日時間軸驗證此概念；頂部切換日期，並提供直式行程清單供閱讀。使用者不必同時理解多軌排程，實際行程仍是一條可連續執行的路線。

```text
時間刻度   10:00        11:00        12:00        13:00
活動片段   [ 景點 A ]──交通──[ 午餐 ]──交通──[ 景點 B ]
操作        整段拖動：改時段／順序
            拉動邊界：調整該活動開始、結束及停留長度
```

此圖只示意互動，不代表精確時間比例或可行路線。

### 22.2 操作與排程語義

| 操作 | 使用者意圖 | 系統反應 |
|---|---|---|
| 按住片段中央拖動 | 把活動移到其他時間或前後位置 | 先顯示暫定位置；放開後重算交通、排隊與後續排程 |
| 拉下邊界 | 延長／縮短停留，保持開始時間 | 更新結束時間，試算對後續活動的影響 |
| 拉上邊界 | 提前／延後開始，保持結束時間 | 更新開始與停留長度，檢查前一站能否及時抵達 |
| 從候選清單拖入 | 增加景點或生活安排 | 建立活動、補入相鄰交通、更新三項額度 |
| 點擊片段／時間 | 查看細節或精確設定 | 顯示時間、停留、固定窗口、推薦理由及未知資料 |
| 縮放／捲動時間軸 | 在整日概覽與局部細調間切換 | 改變顯示比例，不改變行程時間 |

拖動整段時保留原停留長度。拉伸時顯示即時時間標籤及停留分鐘，並可吸附刻度；固定預約保留實際時間，不為顯示刻度而被改動。短活動可點選後開啟較大的調整控制，不能因文字太長就讓片段長度誤代表實際時長。

### 22.3 自動銜接、空檔與衝突

- 交通顯示為活動間的連接片段，候車包含於所屬交通；景點排隊是該景點的等待區段。兩者由服務或標示的估算產生，不能像遊覽停留一樣任意拉短。
- 延長停留先使用相鄰可用空檔，再預覽順延後續未鎖定活動的結果。放開後更新草案，列出被連動修改的活動並提供還原。
- 遇到固定預約、最後入場、最晚入住或取件時間時，不自動推動鎖定活動，也不讓重疊變成已驗證的正式行程；在衝突位置顯示原因與處理選項。
- 拖到另一活動位置時顯示插入或重排預覽；實際時間軸不採多軌同時遊覽兩個地點。新交通不足以銜接時提出衝突。
- 拉短停留需保留合理最短時長；使用者明確要快速到訪時可修改活動類型或停留設定，但不能藉此繞過固定預約與其他必要任務。
- 空白區段顯示為自由時間／緩衝，可被活動使用；必要的步行、候車和已知排隊不能當成空檔刪除。
- 變更遊覽長度本身不直接扣交通＋景點等待額度，但到訪時段改變可能影響交通和排隊，仍需重算。精力與花費也依實際估算規則更新，不按片段長度憑空換算。

### 22.4 額度與確認

時間軸上方持續顯示「步數／精力、花費、交通＋景點等待」三項額度，另顯示當天結束時間。拖動中標示預覽，放開後合併請求並計算，不隨每個觸控事件呼叫外部服務。

第一版建議、每次拖動、拉伸及跨日移動，都保留草案版本。使用者可以還原；只有按下確認才儲存正式行程。未知等待或交通資料仍明確標示，不讓視覺上排得下的片段被誤解為已確認可行。

此版規格以影片剪輯的「片段移動＋邊界拉伸」為主要概念；具體方向、縮放及把手尺寸需透過 iOS／Android 原型實測後定案，尚未實作 App。

## 23. 直向時間軸與本機實作（v1.6）

使用者確認直向較符合手機閱讀方式。採左側時間、右側活動片段，上下拖動把手改順序、拉下緣調整停留，點編輯指定時間或日期。雷達圖可展開，避免佔滿主要排程區。已在獨立分支實作本機示例原型，未重做問答頁面；實際功能、測試與資料限制見專案 docs/SCHEDULE-EDITOR.md。本文其餘內容仍包含後續目標，不代表所有真實資料服務已接入。
